# Exact-head artifact DAG

Expensive deterministic build output should be produced once for one exact source head and then transported to every downstream validation or delivery lane that needs those bytes.

The standard shape is:

```text
source checks
    |
    v
build-artifact.yml
(exact source SHA + semantic artifact key + deterministic identity)
    |
    +--> integration/package validation
    +--> browser/E2E validation
    +--> runtime/performance evidence
    +--> link/Storybook/site validation
    +--> Pages/deployment
```

## Producer rule

Use `build-artifact.yml` as the single producer for a specific expensive artifact identity. Enable `reuse_across_runs: true` when the bytes may be reused by a later workflow run for the same exact identity.

The producer owns only transport and identity. Repository commands still own how the artifact is built, and release qualification remains separate.

## Consumer rule

Downstream jobs must consume the producer outputs rather than rerunning the build command:

- `producer_run_id`
- `receipt_artifact_name`
- `artifact_name`
- `artifact_digest`
- `source_sha`
- `artifact_key`
- `identity_digest`

Reusable consumers accept these as the `prebuilt_*` coordinates. Bespoke jobs should use `.github/actions/consume-build-artifact` with the same coordinates.

Coordinates are all-or-none and are verified against the retained Execution Receipt before extraction. Do not fall back to locally generated bytes after a prebuilt artifact was requested; failure to prove identity is a validation failure.

## Skip provably unaffected Pages builds

**Owner decision (2026-10-13, `/steer reusable-workflows` question 12 — B: skip unaffected Pages builds).**

Always run the repository's established fast validation and preserve required check identities. A Pages
build may be omitted when the repository can deterministically demonstrate that the change cannot
alter that Pages artifact. This applies to ordinary PR and main-branch work, but not to an explicitly
requested validation or delivery that actually requires a freshly produced artifact.

- Derive impact conservatively from the site's real inputs, including source, workflow catalog YAML,
  build scripts, configuration, dependencies, generated metrics/history, and indirect imports.
  Documentation extensions alone are not proof that the published site is unchanged.
- If any changed input is relevant or uncertain, run the existing producer as before. Incomplete
  diffs, unavailable base revisions, or ambiguous dependencies must not cause a skip.
- Avoid a generic validation-impact engine, reusable success-evidence framework, or new
  environment-fingerprint gate. The rule concerns only a proven-unaffected Pages artifact.
- Keep fast validation, workflow syntax checks, and the existing required check names and outcomes.
  Do not use whole-workflow path filtering that leaves required status checks pending.
- Do not strand E2E, Storybook, link, or deployment consumers that require the producer's verified
  artifact. Requested full/browser checks and meaningful delivery must retain their required
  validated bytes. An unaffected source change must not be misreported as a newly deployed site.
- Demonstrate a real skip, a relevant-change rebuild, and an unknown-impact rebuild. Measure job
  starts, setup cost, and total CI effort so this optimization does not cost more than it saves.

This is a bounded repository-owned CI efficiency rule, not a change to validation semantics or
a fleet-wide guarantee that arbitrary source revisions share reusable test evidence.

## Cross-workflow ordering

Cross-run reuse does not deduplicate two producers that start concurrently. When deployment would otherwise race validation, trigger the delivery workflow from the successful validation workflow (`workflow_run`) and use `workflow_run.head_sha` as the source coordinate. That ensures the validated producer exists before the delivery workflow resolves reuse.

Manual dispatches may still invoke the producer; a cache miss intentionally rebuilds through the same deterministic contract.

## Artifact granularity

Do not create one universal artifact merely to maximize reuse. Define a stable semantic artifact per real build boundary, for example:

- packed package
- browser/WASM runtime
- deployable Pages site
- generated corpus or fixture bundle

If two consumers require the same bytes, they should share the producer. If their required bytes or build coordinates differ materially, they should use separate artifact identities.

## What not to memoize

Do not treat mutable test results, environment-dependent observations, or release qualification as ordinary build artifacts. Performance and runtime evidence may be preserved and transported, but their domain schema and verdict policy remain owned by the producing repository/runtime-profiler/Moonlight boundary.

## Adoption checklist

1. Find repeated build commands across CI jobs and workflows.
2. Group repetitions by identical semantic output, not merely similar command text.
3. Create one `build-artifact.yml` producer per output.
4. Remove downstream build commands and pass verified producer coordinates instead.
5. Order cross-workflow delivery behind validation where concurrent producers would race.
6. Keep source-only checks independent when they do not require built bytes.
7. Verify a second run reports reuse and that consumers reject mismatched coordinates.
